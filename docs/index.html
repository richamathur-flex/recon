§01 · Briefing

What is this, and why build it?

Equity research and competitive intelligence are high-leverage but profoundly boring workflows. An analyst spends hours stitching together prices, filings, reviews, and news into a single summary — work that is pattern-heavy, data-aggregating, and summarization-dominant. Three tasks LLMs happen to be excellent at.

The Scope

Recon is a research agent platform. It is not one application — it is a domain-agnostic orchestration layer onto which verticals plug in. A vertical is a bundle of agents, data sources, and prompts tuned to a specific research domain.

  • Vertical 1 — Competitive Intelligence. The flagship. Teardowns, tracking, market briefs across 8 data sources (websites, jobs, reviews, funding, etc.).
  • Vertical 2 — Equity Research. Secondary vertical. SEC 10-K analysis, real-time quotes, Reddit sentiment. Proof that the platform generalizes.
  • Interfaces. Slack bot (primary), FastAPI REST (secondary), CLI (developer).

The Purpose

Two layers of purpose:

Product layer

Turn a natural-language research question into a structured, source-cited brief, delivered to Slack in under 60 seconds.

Portfolio layer

Demonstrate — to interviewers, hiring managers, and future collaborators — competence across the full modern AI engineering stack: LLM orchestration, hybrid retrieval, agent design, system architecture, and deployment.

North Star Build something a stranger finds genuinely useful, not just impressive.

Why this project beats a generic RAG clone

Differentiator 01

Pluggable verticals

Most tutorial projects hardcode one domain. Recon treats the domain as configuration — new research domains can be added without touching orchestration.

Differentiator 02

Hybrid retrieval

Not just dense embeddings. Combined BM25 + dense + reciprocal rank fusion, with metadata-filtered queries per company and per time window.

Differentiator 03

Evaluation built-in

RAGAS metrics, a custom eval set, and regression tests in CI. Most portfolios skip this. Ours reports retrieval precision and faithfulness.

§03 · Specialist Agents

Why we use agents, not just one big prompt

A naive approach to this project would be: stuff everything into one giant LLM prompt and hope. That fails. Agents are how you build reliable AI systems. Here's the philosophy, the pattern, and what each agent does.

The case for specialist agents

Why one giant prompt fails

If you ask an LLM to "research Linear comprehensively", three things go wrong:

  1. Context window explosion. You can't fit a homepage + job postings + reviews + filings + news into one prompt.
  2. Output entropy. The longer the answer, the more the model drifts, hallucinates, and forgets earlier instructions.
  3. No parallelism. One sequential prompt cannot fetch from five APIs simultaneously.

What agents fix

An agent is a small, specialized worker with one job, one prompt, one output schema. By splitting the problem:

  1. Each prompt stays small. Fits comfortably in context.
  2. Each output is validated. Pydantic catches errors per-agent, not at the end.
  3. Agents run in parallel. asyncio.gather lets five agents work concurrently — a 5x latency win.
Interview Soundbite "I split the problem into specialist agents because reliability scales with prompt simplicity. One LLM call doing one job with one schema is testable; one LLM call doing six jobs is not."

The five-step agent pattern (memorize this)

Every agent in Recon follows this same skeleton. Once you understand it for one agent, you understand them all.

1

Fetch — get raw data from a source

httpx · Playwright · official API SDKs

The agent calls an external data source: a website, a JSON API, an RSS feed, a database. No interpretation yet — just retrieval.

2

Clean — remove noise, keep signal

selectolax · regex · structural parsing

Strip HTML scripts and navigation, normalize whitespace, truncate to fit the LLM context window. The cleaner the input, the cheaper the output.

3

Prompt — ask the LLM with a strict contract

Groq · JSON mode · system + user message

System prompt defines the agent's role and output schema. User message contains the cleaned data. response_format={"type": "json_object"} guarantees parseable JSON.

4

Parse — JSON string to dict

json.loads

The LLM returned a string. Convert it to a Python dict. If parsing fails, retry with the error message in the prompt — self-healing.

5

Validate — dict to typed object

Pydantic v2

Pass the dict to a Pydantic model. If any field is missing, malformed, or the wrong type, validation raises immediately. The output is now provably correct.

The synthesizer — the agent above the agents

Final Stage Once the eight specialists return their outputs, a Synthesizer agent reads them all, resolves contradictions ("hiring says expansion; reviews say layoffs"), and writes the final research brief. This agent's output IS the report the user sees in Slack.

How agents communicate — shared state

Agents don't call each other directly. They read from and write to a typed shared state object (a TypedDict in LangGraph). The orchestrator passes this state through the graph; each agent enriches it.

class ResearchState(TypedDict):
    query: str
    companies: list[str]
    web_intel: dict[str, CompanyProfile]
    hiring: dict[str, HiringSnapshot]
    pricing: dict[str, PricingSnapshot]
    sentiment: dict[str, SentimentReport]
    momentum: dict[str, CompanyMomentum]
    final_report: str | None

This is what makes the system testable, debuggable, and extensible. A new agent just adds a new field to the state.

How a query moves through the system

The eight-step lifecycle

1

Input reception

Slack Bolt SDK · Socket Mode

User sends @recon teardown Linear vs Jira in Slack. The Bolt app receives the event over a WebSocket (Socket Mode), authenticates the workspace, and dispatches to the command handler.

2

Query parsing

LangGraph node · Groq Llama 3.3 70B

The first graph node uses the LLM in JSON mode to extract structured intent: { "intent": "teardown", "companies": ["Linear", "Jira"], "focus": ["product", "pricing", "momentum"] }. Typed state flows through the rest of the graph.

3

Strategy planning

LangGraph conditional edges

A planner node decides which specialist agents should fire. For a teardown, it fans out to all 5 agents. For a pricing-only query, only the Pricing agent runs. This is cost and latency optimization, not hardcoded logic.

4

Parallel data collection

asyncio.gather · httpx · Playwright

Agents run concurrently. Web Intel fetches homepages, Hiring scrapes job boards, Sentiment queries G2 reviews. Each agent writes its findings (both raw text and structured data) back into shared state.

5

Corpus indexing

Nomic Embed v1.5 · Pinecone

New documents are chunked (semantic splitting), embedded with a local Nomic model, and upserted to Pinecone with metadata {company, source, scraped_at}. This happens in the background; queries can filter by company.

6

Hybrid retrieval

BM25 + dense + Reciprocal Rank Fusion

For questions requiring context, Recon runs both sparse (BM25 for exact terms like pricing tiers, product names) and dense (semantic) retrieval over the corpus, then merges the ranked lists via RRF. The fused top-K goes into the synthesizer prompt.

7

Synthesis

Groq · Pydantic structured output

The synthesizer node receives all agent outputs and retrieved context, prompts the LLM to generate a structured report following a Pydantic schema (executive summary, per-company deep-dive, comparison table, action items). Structured output means no markdown parsing fragility.

8

Delivery

Slack Block Kit · Thread reply

The Python-side formatter converts the Pydantic report into Slack Block Kit JSON. Response posts as a threaded reply so the channel stays clean. Interactive buttons ("Track this", "Re-run in 7 days") are attached for follow-up workflows.

Interview Gold The Strategy Planner (step 3) is the single most interview-worthy architectural detail. It's how you answer the question "why not just use a ReAct agent?" — because a ReAct agent can't plan parallel execution; a graph can.

Step 9 — Write and run the smoke test

Create the file scripts/smoke_test.py with the contents below. This proves Pinecone + embeddings + Groq all work before you build anything else.

import os
from dotenv import load_dotenv
from pinecone import Pinecone, ServerlessSpec
from sentence_transformers import SentenceTransformer
import httpx

load_dotenv()

# 1. Pinecone setup
pc = Pinecone(api_key=os.getenv("PINECONE_API_KEY"))
index_name = os.getenv("PINECONE_INDEX_NAME", "recon-v1")

if not pc.has_index(index_name):
    pc.create_index(
        name=index_name,
        dimension=768,
        metric="cosine",
        spec=ServerlessSpec(cloud="aws", region="us-east-1"),
    )

index = pc.Index(index_name)

# 2. Embedding model (downloads ~500MB first time)
embedder = SentenceTransformer(
    "nomic-ai/nomic-embed-text-v1.5",
    trust_remote_code=True,
)

# 3. Grab a test page
html = httpx.get("https://linear.app", timeout=30).text
chunk = html[:2000]

# 4. Embed and upsert
vec = embedder.encode(chunk).tolist()
index.upsert([{
    "id": "linear-home-1",
    "values": vec,
    "metadata": {"company": "Linear", "type": "homepage"},
}])

# 5. Query
q = embedder.encode("project management for software teams").tolist()
res = index.query(vector=q, top_k=3, include_metadata=True)

for m in res["matches"]:
    print(f"score={m['score']:.3f}  meta={m['metadata']}")

print("✅ Pipeline working")

Follow Conventional Commits. Recruiters scanning your repo will notice.

  • feat: new feature — feat: add reddit sentiment agent
  • fix: bug fix — fix: handle empty pinecone response
  • docs: documentation — docs: update setup instructions
  • refactor: non-behavior code change — refactor: extract vector store interface
  • test: adding tests — test: cover parse_query edge cases
  • chore: maintenance — chore: bump langgraph to 0.3
  • ci: CI config — ci: add ruff to pipeline

Fixing mistakes

git restore src/broken.py                   # discard unstaged changes to file
git restore .                               # discard ALL unstaged changes
git reset HEAD src/file.py                  # unstage a file (keeps changes)
git commit --amend -m "new message"         # fix last commit message
git revert <commit-sha>                     # undo a commit safely (creates new commit)
Warning Never git push --force on main. It rewrites history and will break anyone else's clone. Use --force-with-lease on your own feature branches only.

When you accidentally commit a secret

It happens. Here's the recovery sequence:

  1. Immediately rotate the leaked key at the provider (Pinecone, Groq, etc.)
  2. Remove it from the code and add to .gitignore (if it wasn't already)
  3. Commit the fix, push
  4. If the commit hasn't been public long, you can rewrite history with git filter-repo. Otherwise accept that it's burned and only rotate.

The single most useful async pattern to memorize

import asyncio

async def run_all_agents(query: str) -> dict:
    # Launch all agents concurrently
    results = await asyncio.gather(
        web_intel_agent(query),
        hiring_agent(query),
        sentiment_agent(query),
        pricing_agent(query),
        return_exceptions=True,   # don't fail all if one fails

    return {

        "hiring": results[1],
        "sentiment": results[2],
        "pricing": results[3],
    }

§10 · Field Notes

Real errors hit, real fixes applied

A log of every problem encountered while building Recon, what caused it, how it was solved, and what to say about it in interviews. These are not hypothetical — they actually happened.

Error 01 · ModuleNotFoundError: No module named 'src'

When · Day 2 · First agent run

The symptom

Traceback (most recent call last):
  File "scripts/run_web_intel.py", line 20, in <module>
    from src.agents.web_intel import analyze_company
ModuleNotFoundError: No module named 'src'

The cause

Running python scripts/run_web_intel.py tells Python that scripts/ is the root of imports. From there, src/ looks like a sibling folder, not an importable package, so the import fails.

The fix

# ❌ This fails — Python can't see src/
python scripts/run_web_intel.py https://linear.app Linear

# ✅ This works — -m makes Python treat the project root as the package root
python -m scripts.run_web_intel https://linear.app Linear

Going forward

Always use python -m scripts.<name> ... — no .py extension, dots instead of slashes. This is also the standard way to run pytest, uvicorn, and most professional Python tools.

Interview answer

If asked about Python imports "Python's import system uses the location of the entry-point script as the root. python file.py sets that root to the file's directory; python -m package.module sets it to the project root. For multi-package projects, you always want the latter — otherwise relative imports break."

Error 02 · GH013: Repository rule violations · GitHub Push Protection

When · Day 2 · First push of agent code

The symptom

remote: error: GH013: Repository rule violations found for refs/heads/main.
remote: - GITHUB PUSH PROTECTION
remote:   - Push cannot contain secrets
remote:   --- Groq API Key ---------------------------------
remote:     locations:
remote:       - commit: a8866f51c0f1b23c7e10159ea537e8fb46946f35
remote:         path: .env:1
! [remote rejected] main -> main (push declined due to repository rule violations)

The cause

The .env file containing the real Groq API key was accidentally committed and pushed. GitHub's secret scanning detected the key and refused the push. This is GitHub doing you a favor — without this protection, the key would have been public.

The fix

# 1. Untrack .env (keeps the local file)
git rm --cached .env

# 2. Amend the commit to remove .env from history
git commit --amend --no-edit

# 3. Force push the rewritten commit
git push --force

Critical follow-up

Even though the key never reached GitHub publicly, it was in your local Git history. Rotate the key anyway. Go to console.groq.com → API Keys → delete the old one → create a new one → update .env. Treat any key that appeared in any commit as compromised.

Prevention going forward

  • Verify .gitignore contains .env before any git add
  • Run git status before every commit and scan for sensitive files
  • Consider installing git-secrets as a pre-commit hook for an extra safety net

Interview answer

If asked about secret management "I treat the .gitignore as a security boundary, not a convenience. I had a near-miss early in this project where a .env file got committed; GitHub's secret scanning caught it before it went public, I amended the commit, and rotated the key. The lesson stuck — I now scan git status before every commit and never treat .env as anything but radioactive."

Error 03 · __pycache__ folders cluttering Git

When · Day 2 · After running scripts

The symptom

After running scripts, Git started tracking .pyc files inside __pycache__/ folders:

create mode 100644 src/__pycache__/__init__.cpython-314.pyc
create mode 100644 src/__pycache__/config.cpython-314.pyc
create mode 100644 src/agents/__pycache__/web_intel.cpython-314.pyc

The cause

Python compiles .py files into .pyc bytecode at runtime, storing them in __pycache__/ folders. These are auto-generated, machine-specific, and should never be committed. Either .gitignore didn't list them, or they were accidentally tracked before the rule was added.

The fix

# Add to .gitignore (if not already there):
# __pycache__/
# *.py[cod]
# *.pyc

# Untrack already-committed pycache folders
git rm -r --cached src/__pycache__ src/agents/__pycache__ scripts/__pycache__

git commit -m "chore: remove python cache files"
git push

Why this matters

Beyond clutter, committed .pyc files can cause subtle bugs across machines (different Python versions produce different bytecode). Keeping them out of Git is a hard rule in every Python project.

Interview answer

If asked about .gitignore best practices "I keep three categories out of Git: secrets (.env, keys), build artifacts (__pycache__, dist/), and IDE config (.vscode/). The .gitignore goes in the very first commit, before any other code. If I miss something and it gets committed, git rm --cached removes it from tracking without deleting the local file."

The general debugging mindset

Across all three errors, notice the pattern:

  1. Read the error message carefully. Each one literally told you the problem.
  2. Understand the cause, not just the fix. Why did Python lose src? Why did GitHub block the push?
  3. Apply the fix. Often a single command.
  4. Prevent recurrence. Update .gitignore, change your default command, document the lesson.

Engineers aren't people who don't make mistakes — they're people who recover well from them and don't repeat them.
